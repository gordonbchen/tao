# Tao: project guide for future agents

## Purpose and current stage

Build a course-aware learning website. A student creates subjects, supplies their own course material, practices problems drawn from what their course has covered, and receives topic-level spaced review. Keep the app and student data local first. A hosted version may come later, but local use must remain a complete path.

This file is the living record of the project's direction. Update it in the same change whenever a product decision, architecture, setup command, test command, or important assumption changes. Keep it accurate and short enough to use. Record unresolved decisions as unresolved; do not present proposals as completed features.

## Implemented local prototype

The Next.js app, PostgreSQL schema and auto-applied migrations, Docker Compose development setup, subject/topic/resource pages, text and PDF text extraction, resource summaries, topic suggestions, single-problem study screen, Codex CLI, Claude Code CLI (`claude -p`), and OpenCode (`opencode serve`) backends, and topic review scheduling are implemented. On another Docker machine, use `docker compose -f compose.portable.yaml up --build` and open `http://localhost:6283`; see the README for login and checks. This workspace uses `docker compose up --build` with `compose.yaml`, a Linux host-network variant because its Docker environment cannot create bridge interfaces. Each AI sidecar (Codex, Claude, OpenCode) always starts, uses its own Unix socket and login volume, and is signed in or out from the header's AI accounts dialog, which drives the CLI's own login flow (`bridge/auth.mjs`); the selected model decides which sidecar handles a request. No `.env` or host CLI is needed. Run `npm run typecheck`, `npm run lint`, `npm test`, and `npm run build` for checks, or run typecheck/lint/tests inside the web container. `README.md` has a short test walkthrough.

The current `local-demo` owner is shared by all visitors and there is no sign-in. Do not deploy this prototype as a public multi-user service. Scanned PDF OCR, mixed-subject study, problem queue UI, and production VPS configuration are not implemented.
The study page (`app/study/[subjectId]/`) has Problems and Flashcards tabs (last one kept in localStorage) and a topic picker for any mix of topics and folders; the URL carries both (`?mode=cards&topic=…&group=…`), and `lib/selection.ts` turns the selection into SQL for both modes. An empty selection means every topic. Flashcards (`cards`) have a front, back, optional topic (deleting the topic keeps the card, unfiled), and FSRS state from `ts-fsrs` with default parameters and no fuzz (`lib/flashcards.ts`); every rating is logged in `card_reviews` with the scheduler's log. The next card is a due learning card, then a due review, then a new card; learning cards due within 20 minutes are shown early when nothing else is due. There is no daily new-card limit. Cards are added by hand, imported (`lib/card-import.ts`: Anki `.apkg`/`.colpkg` via `node:sqlite` and zstd for `collection.anki21b`, or tab/comma text with Anki's `#separator`/`#html` headers; HTML is flattened, cloze notes become one card, media is dropped), or generated and shown for review before saving: the Generate dialog picks topics and folders with the study page's picker, starting from the current selection, and drafts cards for each covered topic (one request per topic, three at a time), streaming each card into the review list as soon as the model finishes it, and saving each under its topic. The route replies with one JSON line per card (`application/x-ndjson`, read by `aiStream` in `app/components.tsx`); `generateCards` pulls finished cards out of the partial output with `completeArrayItems` (`lib/partial-json.ts`). Only the Claude sidecar streams: asked with `stream: true`, it has the CLI write the JSON as plain text (the API sends structured output only once it is complete) and passes on `text_delta` pieces, then checks the whole reply; Codex and OpenCode send a topic's cards together. Most of the wait before the first card is the model's hidden thinking. An optional Instructions box adds the student's own request to the prompt (`studentInstructions` in `lib/ai.ts`, at most 1,000 characters, kept in the saved metadata); it cannot change the output format or leave the course material. Drafts live in a per-subject store outside the dialog (`startGeneration` in `cards.tsx`), so closing the dialog, changing the selection, or moving around the app keeps them coming; the toolbar's Generate button shows the progress and reopens the review. Stop keeps the drafts so far, and Discard drops them; both stop the unfinished requests (see Stopping AI requests below). Reloading the page loses unsaved drafts and also stops the model. To keep one idea from becoming a card under every topic that mentions it, each topic's request lists the other topics sharing its resources (their ideas are left to them) and the fronts of every card on those resources plus the drafts written so far in the run (`avoidFronts`); the route also drops a card whose front matches one of those after `frontKey` (`lib/flashcards.ts`) ignores case, punctuation, and leading filler. Generation's default count is Auto: a card for each idea central to the topic that existing cards miss (usually 3 to 10, possibly none, at most `AUTO_CARD_LIMIT`, 15); the student can instead pick any count from 1 to 30 per topic. A card density select (Brief, Standard, Detailed; remembered in localStorage) sets how much each card asks and how long its back runs. Flashcards need no AI; chat and generation do. `app/chat.tsx` is the tutor chat for both problems and cards: a one-line input that grows, Enter to send, a lightbulb hint button beside Send. Unsent chat messages and problem answers are saved in localStorage as they are typed (`readDraft`/`saveDraft` in `app/components.tsx`, keyed per chat or problem) and cleared on send or submit. `tutor_messages` belongs to exactly one problem, card, topic, folder, or resource; card chat tells the model whether the back has been shown, and before that it only hints. Problem and card chats have Summarize beside Send and a Clear chat button in a bar at the top (`DELETE /api/problems/[id]/hints`, `/api/cards/[id]/chat`): clearing sets `cleared_at` as starting a new study chat does, but they keep no list of earlier chats, and a problem's answer checks are left alone. Their tutor reads the latest summary plus the replies since it (`currentChat`, `summarizeStoredChat`, `clearStoredChat` in `lib/study-chat.ts`). Topic, folder, and resource viewers have a Chat tab, and from the `split` breakpoint (56rem, `globals.css`; the chat column is at most 28rem or 45%) also show the chat beside the Summary tab (it stays in view while the summary scrolls; a button at the end of the tab row hides it, remembered in localStorage); the Chat tab's chat fills the viewer's width. Wherever a chat sits beside other content from the `split` breakpoint (viewer summaries, the subject page, problems, and cards), an Enlarge button in its top bar opens the same chat in a wide modal; Escape or Shrink returns it (`lib/study-chat.ts`, `/api/{topics,groups,resources}/[id]/chat`) for open questions outside practice: no lightbulb; Summarize beside Send, and Earlier chats and Start a new chat in a bar at the top of the chat. Starting a new chat archives the current one (`tutor_messages.cleared_at` is set, never deleted); the history button opens a chat list, as in a chatbot: the current chat, then archived ones by last message (`GET …/chat?archived=1`), and New chat. Clicking an archived chat makes it current again and archives the one it replaces (`DELETE …/chat?restore={clearedAt}`). Each study chat has a name, shown in the top bar and the archive list: the model titles an unnamed chat in its next reply (the `chat` schema's `title`, empty otherwise), and the pencil renames the current chat (`PATCH …/chat`); an unnamed chat shows its first question. The name is a `title` row in `tutor_messages`, so it is archived with its chat. Only messages with no `cleared_at` reach the tutor. A line above the input says when older messages no longer fit and offers Summarize. Summarize stores a `summary` row that stands in for everything before it; the model gets the latest summary plus up to the last 12 later messages, up to 20,000 characters (`recentMessages`, `sinceSummary` in `lib/chat-context.ts`), and the item's material: a topic's coverage summary and linked excerpts, a folder's summary and contents' briefs, or a resource's summary and up to 24,000 characters of its text (the opening plus the passages sharing the most words with the student's messages, `lib/chat-context.ts`). The subject page has the same chat behind a toggle beside Practice (closed by default, kept in localStorage; below `split` it sits above topics and resources; `/api/subjects/[id]/chat`) for questions about progress, weak areas, and what to study next. Its material (`lib/subject-context.ts`) is a compact record per topic (folder, brief, review schedule or "not practiced yet", attempt, skip, and opened-but-unanswered counts, card counts, lapses, and 30-day forgotten reviews, with zero values left out), the 12 most recently active served problems with their status, the 8 latest topic, folder, and resource chats (current or archived) with their names and last three questions, resource filenames with briefs and dates added, and the full coverage summary of at most two topics whose names the conversation mentions (`mentionedItems`); no resource text is sent. Every chat reply (problem hints, card chat, and these study chats) uses the bridge's `chat` schema: `reply` text plus an optional `diagram`, stored in `tutor_messages.diagram` and drawn under the message. Chats may draw, but only when the student asks or a figure clearly helps; hint and unrevealed-card figures must not give the answer away. The tutor reads earlier figures as their `alt`. Chat summaries still use the `hint` schema.
Diagrams (`lib/diagrams.ts`, `app/diagram.tsx`) are optional figures stored as `{kind: "mermaid" | "svg", source, alt}` in `problems.diagram`/`solution_diagram` and `cards.front_diagram`/`back_diagram`. Problem generation lets the model decide, asking for a figure only when the problem refers to one or it clearly helps. Card generation draws figures only when the Generate cards dialog's diagrams checkbox is on (off by default, remembered in localStorage). Every drawing prompt shares one test (`DIAGRAM_TEST` in `lib/diagrams.ts`): draw only for spatial ideas or parts too tangled for words, never for what a sentence or two says as well; even with the checkbox on, most cards get none. Existing figures are always shown. Mermaid renders in strict mode with init directives stripped; SVG is shown through an `<img>` data URL, so it cannot run script or load anything, with color names (`ink`, `accent`, …) mapped to the current theme's tokens. The tutor and answer checking see only `alt`, which may hold `\(…\)` math: it is typeset in the enlarged figure's subtitle and the can't-draw message, and screen readers get it without delimiters (`plainAlt`). Chat replies can carry figures too (see above). Mermaid loads only when a figure needs it. Flowchart labels may hold TeX between `$$` and `$$`, which Mermaid typesets with its bundled KaTeX (not MathJax; other Mermaid diagram types, sequence diagrams included, get plain Unicode math, since Mermaid draws their math unreliably). Mermaid drops the spaces beside each formula, so `spaceMermaidMath` repeats them inside it as `\ `. That math is MathML set in Libertinus Math (`@fontsource/libertinus-math`, declared in `globals.css` without Fontsource's Latin-only range, and loaded before Mermaid sizes the boxes; the same rules cover Mermaid's measuring div, `#dtao-diagram-N`, and align formulas to the text baseline). Prompts ask for quoted flowchart labels; a flowchart that does not parse is tried again with its labels quoted (`quoteMermaidLabels`), since an unquoted `(` inside `A[…]` is the usual failure. A figure that still fails to draw shows its description. Clicking a figure opens it enlarged in a wide modal; Escape closes only the topmost modal, and viewer and card shortcuts pause while another dialog is open. Generated figures are unverified; SVG geometry in particular can be wrong.
Stopping AI requests: every AI action the student waits on can be stopped. Chat Send becomes Stop while a reply or chat summary is written (a stopped question goes back to the input); problem generation and answer checking, resource, topic, and folder summaries, Organize (also by closing its dialog), Suggest, and New topics show Stop beside their spinner. The page sends these with `aiApi` (`app/components.tsx`), which adds an `x-tao-request-id`; aborting it calls `DELETE /api/ai/requests/[id]`, which aborts that request's signal (`aiOptionsFromRequest`, `cancelAiRequest` in `lib/ai.ts`). The bridge call then closes its socket, and each sidecar kills its CLI (Codex, Claude) or aborts its session (OpenCode) when the connection closes. A dropped connection alone does not stop a request, so replies and summaries still finish and save when the page reloads. A cancelled summary restores its previous status, and a cancelled hint does not fall back to a stored one. Uploads (topic suggestions during upload) cannot be stopped.
Resource upload accepts multiple files in one picker action and processes each one, queuing its topic suggestions for review. The review dialog adds or links one suggestion, all of a file's (Add all), or every queued file's, one request per file (`POST /api/subjects/[id]/topics` with `names` and `resourceId`); each button shows a spinner while it works. Topic summaries triggered by adding or linking run two at a time, because each is a long request and many at once would stall every other request from the page. It extracts selectable PDF/text content; files may be up to 200 MB, since lecture PDFs are mostly images and only their text is stored. Codex suggests study topics from sampled material throughout the extracted text, using existing topic names when they fit. Headings and the filename are a fallback when Codex is unavailable. If Codex is connected, it generates a per-resource summary from the full extracted text in sections. Students can click a resource name to inspect its Markdown and MathJax summary or extracted text in a wide viewer that closes with Escape. In a topic or resource viewer, Tab and Shift+Tab cycle its tabs and Left/Right open the previous or next item; keys typed in fields behave normally. The resource/topic summary viewer has one vertical scroll area: the modal itself. Wide modals are flex columns of a fixed height (the screen less a margin), so loading or switching tabs never resizes them and the Chat tab fills the height left under the title and tabs. `resources.extracted_text` stores the full extracted text (up to 200,000 characters), while resource summary fields store generated text and model provenance. Topics store name, coverage flag, review state, and an editable Markdown and MathJax coverage summary generated from explicitly linked resources. The topic Resources tab shows selected rows and a searchable list of available rows; clicking a row stages the link change. Save replaces its link set and triggers one summary regeneration. Track saving, summarizing, and errors by topic ID so one topic's model work does not block another topic's Save action or overwrite another topic's open view. The resource viewer's Topics tab uses the same staged picker in reverse; its Save replaces the resource's topic links and regenerates each changed topic that still has resources. Accepting a topic suggestion also links the resource and regenerates the summary. Each resource and topic summary call also returns a one- or two-sentence `brief`, stored in its own column. The picker's Suggest button asks the selected model to rank unlinked candidates by their briefs (first 300 summary characters when a brief is missing) against the open item's summary; up to five sort first in the add list with a Suggested badge. Suggestions run only on request, are not stored, and never link anything without Save. A `topic_resources` join table connects them. Topics can be arranged in nested folders (`topic_groups`, up to four levels deep; topics are always leaves, with `topics.group_id`). Folders collapse (state kept per subject in localStorage), and rows move by dragging or with the edit row's folder select. Folders and topics share one student-chosen order within each parent (`position`, a float; new rows default to the current epoch so they go last, and a drag stores the midpoint of its new neighbors). Dropping on a row's top or bottom edge places the item before or after it; dropping on a folder's middle puts it last inside. Right-clicking a row (or the context-menu key, or a … button shown on touch screens) opens its menu: Edit, a new folder (inside a folder, or beside a topic), a new topic inside a folder, and Delete. The New folder button beside Topics creates top-level folders. Deleting a folder deletes everything inside, with the usual undo toast. A folder's resources are the union of its descendant topics' links. Its summary is a short overview written from its direct contents' briefs, never from resource text; it is stale when the hash of that input differs from `summary_basis`. Topics can also be unorganized (`topics.unorganized`, never in a folder), listed in an Unorganized section below the tree. Upload topic suggestions are plain names (the `topic_names` schema; the model reuses existing names when they fit), and accepting a new one adds it to Unorganized, as does the Add a topic field beside Topics. The resource viewer's Topics tab has a New topics button that asks for suggestions again for that file (`/api/resources/[id]/new-topics`, leaving out topics already linked) and opens the same review list. Topics drag in and out of Unorganized, and the edit row's folder select has an Unorganized option. Dropping a folder on Unorganized warns first, then moves every topic under it there and deletes the folder and its subfolders, with their summaries and chats (`DELETE /api/groups/[id]?keepTopics=1`). The Organize button in the Unorganized section asks the model to place only the unorganized topics in the existing tree, reusing or creating folders (a path through an existing topic's name is cut back so the topic sits beside it, `pathsBesideTopics`). The preview shows the whole tree with those topics marked New, and nothing moves until Apply. Topics the model leaves out stay unorganized, and organized topics never move. Clean up, beside New folder, asks the model to tidy topics: merge ones that overlap or slice one file too thinly, rename unclear ones, and remove ones that are not course material (`POST /api/subjects/[id]/topics/cleanup`). It sends one request per resource with several topics (with the file's summary and word count), plus one for topics linked to no resource, three at a time, and streams each checked change (`checkCleanup` in `lib/topic-cleanup.ts`: each topic in one change, no name clash) into a dialog where the student unchecks what they don't want. Apply (`PUT`) runs in one transaction: a merge keeps the topic with the most review history, then the most cards and problems, under the new name, moves the others' cards, problems, and resource links to it, archives their chats under it, deletes them, and rewrites its summary; a removed topic's cards and problems stay, unfiled. Practicing a folder practices the most due topic under it. See `docs/content-model.md` for the remaining passage-level evidence plan.
Practice content uses locally hosted MathJax 4 to render TeX in problems, hints, feedback, solutions, and a live preview under every text box the student types TeX into (`$…$`, `$$…$$`, `\(…\)`, `\[…\]`; the shared `Textarea`, opted out with `mathPreview={false}` for raw formats such as Markdown summaries and card import; the chat shows its preview above the input). A formula that does not parse is put back as its source text instead of a MathJax error (`restoreErrors` in `app/math-text.tsx`). `npm install`/`npm ci` copies MathJax and its font package into ignored `public/mathjax/` and `public/mathjax-font/`; keep both available in Docker and local development. Ask AI providers for `\\(...\\)` inline and `\\[...\\]` display notation. Practice text is plain text plus MathJax, not Markdown, so its prompts ask for no Markdown markup. `lib/model-text.ts` undoes replies that were JSON-escaped twice (`\\in`, literal `\n`). Chat remains plain text while typing.

Current interface direction: keep the overview to subjects and a new-subject action. A subject page shows the subject name (renamed with the pencil beside it), editable topics, resources with add/remove controls, and a Practice button for any topic; a topic or folder row's right-click menu has Practice and Flashcards for just that topic or folder. Problems are generated only when the student asks, never ahead of time. The Problems tab returns to a served problem with no attempt and no skip in the selection (`GET …/problems/current`), with its chat; otherwise it shows the settings and Make a problem. The settings are Difficulty (Auto, the default, chooses from the topic's review history; or Easy, Medium, Hard) and Answer (Short, Standard, Full: how much the student writes), remembered in localStorage and stored in `generation_metadata`. The form also has an optional Instructions box, sent with every new problem until the student changes it and stored in `generation_metadata`. Next problem and Skip use these settings; the toolbar's New problem opens them in a dialog. With Auto and no instructions, a due problem the student could not solve comes back before a new one. Skipping asks for a new one. The Problems tab's Browse dialog lists served problems in the selection with their latest result; opening one restores its chat and latest attempt (the solution is sent only once an attempt exists), and Try again records a new attempt that updates the topic's review like any other. The Problems and Flashcards Browse dialogs share `app/study/[subjectId]/browse.tsx`: each row has a checkbox, the header checkbox selects every row the search shows (or clears the selection), and the chosen rows can be archived, unarchived, or deleted together (`PATCH`/`DELETE /api/subjects/[id]/{cards,problems}` with `ids`; deletion waits on the undo toast). Rows show prompts and card text on one line with the math rendered inline (`MathLine` in `app/math-text.tsx`; MathJax's page-wide startup typeset is off, so only these components typeset). A Show select filters the list (All, Archived, and per dialog: Not answered, Answered, Wrong or partial for problems; New, Due for cards) and a Sort select orders it (Newest or Oldest first, By topic, and Due soonest for cards), both remembered in localStorage. Archived cards and problems (`archived_at`) stay in Browse under its Archived view but leave review: an archived card is never due, and an archived problem is never returned to or reused. Removal uses a 10-second undo toast instead of a confirmation dialog. Subject descriptions are no longer collected or used; the legacy database column remains to preserve existing data. Home's tab title is `Tao - Home`, subject/study titles use `Tao - {subject name}`, and `app/icon.svg` is a yin-yang favicon and header mark. Keep typography comfortably sized; Libertinus Serif is bundled locally. Remove redundant banners, headings, controls, and copy before adding new ones.
The site header links home and exposes a Connect AI/accounts dialog, model selection across signed-in providers, a remaining-usage bar, and a persistent dark mode toggle; below the `sm` breakpoint these fold into a menu button. Wide modals fill the screen there. Sign-in is not available until accounts exist; do not imply that the shared local workspace is private. Without a signed-in provider, resource text can be viewed but summary and practice actions must open the sign-in dialog.

## Product direction

- Support multiple subjects per student. Each subject has a name and an editable list of covered topics; do not collect a subject description.
- Accept text files and PDFs as course resources. Scanned or handwritten PDFs may be accepted in the first version if extraction is practical, but the student must review and correct extracted topics and coverage. Do not promise reliable handwriting recognition before testing real examples.
- Use locally invoked CLIs as the AI backends: Codex CLI, Claude Code CLI (`claude -p` with structured JSON output, no tools), and OpenCode. The OpenCode sidecar (`bridge/opencode.mjs`) keeps `opencode serve --pure` on a random loopback port with a per-start password and calls its HTTP API: JSON-schema output with only the `StructuredOutput` tool enabled and every permission denied, one session per request, deleted afterwards. OpenCode signs in to one provider chosen in the accounts dialog (device-code OAuth such as ChatGPT or GitHub Copilot, a pasted code, or an API key, which is not checked when saved); only providers with saved credentials count, since its free tier refuses outside clients. Its models are listed live as `provider/model` (text models with tool calling), and a slash in a model ID routes it to OpenCode (`providerForModel`). OpenCode reports no usage. Each calls a hosted model through the user's own login. Remove obsolete provider branches when assumptions change; do not retain Ollama or API-key code paths. Never require a hosted Tao server for local study.
- Select practice topics using a simple, explainable spaced repetition schedule based on attempts. Save the attempt history so the scheduling algorithm can be changed later.
- Save skipped-question reasons and free-text quality feedback with the problem. Use recent feedback and previous prompts to guide future generation, and revisit unsolved problems when due without counting a skip as a failed attempt.
- Generate problems within the student's confirmed course coverage. Target difficulty defaults to Auto, chosen from the topic's attempt history; the student may pick Easy, Medium, or Hard instead, and an answer length. Keep the generated problem, solution, relevant source references, and generation metadata.
- Give each problem a small tutor conversation for hints, explaining where the student is stuck, and answer feedback. Reveal hints incrementally; do not expose the stored solution before submission or an explicit request.
- Ask for a discrete difficulty rating after an attempt (initial proposal: Easy / Okay / Hard / Could not solve). The tutor may suggest a rating later, but the student controls it. A timer and time-based scheduling signals must be optional; do not create pressure to finish quickly.
- Treat AI grading of mathematical reasoning as fallible. Allow uncertain feedback and student correction.
- Keep flashcards separate from problems: their own table, FSRS schedule, and review history; they share the topic selection and tutor chat. Mixed-subject study remains in the longer-term plan.
- Future study-flow ideas: let students park a problem and return to it later with their work intact; offer a session that presents several problems (for example four) together. The first prototype stays with one problem at a time. Parking or generating another problem must not count as a failed attempt or change review state.

## Next content model

The detailed plan is in `docs/content-model.md`. Update it alongside this file when content storage or summary behavior changes.

- Keep the original file and extracted text per resource. Generate a reviewable resource summary only when Codex is connected; show what was extracted even without AI.
- Keep an editable coverage summary per topic and explicit links to its resources. Passage-level support for each claim and multiple distinct passages from the same resource remain planned. When resources change, mark the topic summary stale. A future draft/confirmation flow should preserve student edits when regenerating; do not silently treat new model text as confirmed coverage.
- Derive a subject overview from confirmed topic coverage instead of maintaining a third independent summary. For problem generation, use the topic coverage summary together with relevant source passages, so students can trace the material back to their notes.
- Keep model switching and usage in the header. Open the AI accounts dialog when an AI action needs sign-in. Claude CLI has no usage command; the Claude sidecar reads its subscription login's 5-hour and weekly windows from Anthropic's undocumented OAuth usage endpoint and reports the most used one. Show only real usage data and label unavailable values honestly. Do not imply that Codex inference is offline or free of usage limits.

## Proposed implementation

- Use TypeScript and Next.js for the web interface and its server-side API. Keep one application until a separate backend solves a concrete problem.
- Use PostgreSQL for users, subjects, topics, resource metadata, extracted text, problems, attempts, review state, and tutor messages. Keep original uploaded files outside the database.
- Run the app and PostgreSQL locally with the existing Docker Compose setup. Keep local operation independent of any deployed Tao service and keep database migrations in version control.
- Keep a small VPS deployment as an optional later path, with accounts, HTTPS, backups, and abuse controls. Do not make it the default architecture or a prerequisite for local use.
- Call Codex from server code only. Never bundle login files in source code, write them to logs, commit them, or expose them to another user. Keep the bridge narrow and avoid speculative provider abstractions.
- The Codex and Claude backends use hosted OpenAI/Anthropic inference through local CLI logins; they are not offline models. Keep them local-only. Run each CLI in its own container (`Dockerfile.codex`, `Dockerfile.claude`, `Dockerfile.opencode`, scripts in `bridge/`) with only its login directory mounted; do not mount the web app's database or uploads there. The app sends prompts over per-provider Unix sockets. Logins live in the `codex_auth`/`claude_auth`/`opencode_auth` volumes (or an optional host directory). Do not commit `.codex-tao/`, `.claude-tao/`, or `.opencode-tao/` or include credentials in Docker images. Anyone who can reach the app can manage these logins, which is another reason not to expose the prototype publicly.
- Start with text extraction and relevant excerpts from resources. Add semantic retrieval only when simple topic/source matching is inadequate. Avoid sending all course files with every request.
- Plan for multiple users from the data-model and authorization level, even if initial testing uses one account. Every resource and record must be scoped to its owner.

Revisit design choices when actual constraints justify a change; distinguish planned summary and hosted features from implemented behavior.

## First local milestone

1. Set up the app, local database, migrations, environment example, and documented start commands.
2. Implement subjects, resource upload/extraction, and student review of the covered-topic list.
3. Implement a problem session with topic selection, AI generation, hints, answer feedback, and attempt rating.
4. Persist topic review state and show why a topic is due.
5. Test with representative analysis notes and problems, including a scanned PDF if practical.

Do not require an API key to run the site locally. AI actions require a Codex, Claude, or OpenCode sidecar and login; organizing subjects and viewing extracted text do not.

## Development and code quality

- Prefer no code, then less code. Implement the smallest clear path that satisfies the current behavior. Avoid speculative abstractions, extra services, and duplicate state.
- Follow the UI style guide below for every visual change. Check nearby screens before adding styles, and ensure new controls work in dark mode and at narrow widths.
- Keep `compose.yaml` and `compose.portable.yaml` aligned when app services, volumes, or environment variables change. The portable file is the copyable setup path; the host-network file supports this workspace. Verify Compose config after edits and update README setup commands.
- When an assumption changes, find code that existed because of the old assumption. Remove or simplify it instead of layering a new branch on top.
- Keep domain decisions (topic scheduling, coverage, difficulty, attempt outcomes) separate from UI and AI-provider calls. Make scheduling deterministic and testable.
- Validate untrusted inputs and uploaded files. Enforce file size/type limits and ownership checks at server boundaries. Do not trust generated content as authoritative course coverage or a verified mathematical solution.
- Use database migrations for schema changes. Never commit secrets, uploaded student documents, or local database files.
- Add meaningful tests for scheduling, authorization, extraction edge cases, and AI response handling. Avoid tests that merely repeat implementation details. Run type checking, linting, and relevant tests before declaring a change complete.
- Document actual setup and test commands in README.md once tooling exists. Keep an example environment file with variable names and explanations, never live values.
- For any change, report what changed, how it was checked, and any remaining limitations.

## UI style guide

Tao should look like one calm, well-set printed page, not a collection of widgets. Every screen uses the same small set of sizes, colors, and components. Styling uses Tailwind CSS v4 utilities. When a value you need is missing, add a token to `@theme` in `app/globals.css` or a variant to `app/ui.tsx`; do not add a one-off value. When touching a screen, move nearby drift onto the scales below instead of copying it.

**Tokens.** Raw color values live once in `app/globals.css` on `:root`, with dark values under `[data-theme="dark"]`; `@theme` maps them to Tailwind colors (`bg-paper`, `text-muted`, `border-line`, `bg-danger-soft`, …) and resets Tailwind's default palette, type sizes, radii, and shadows, so only Tao tokens exist. Because tokens swap in dark mode, `dark:` variants are rarely needed. Do not use hex values, arbitrary color or size values (`text-[17px]`), or inline styles except for computed values such as a progress width. Arbitrary values are acceptable only for layout constraints like `grid-cols-[…]` or `max-h-[calc(…)]`.

**Alignment and control height.** Items that sit on one line must share one height and one baseline. This is the most visible defect to avoid.
- Set height with the control tokens, not padding: `h-control` (40px) for buttons, inputs, selects, and segmented controls; `h-control-sm` (32px) for compact rows, chips, and toolbars. Never mix the two sizes in the same row. The shared components already do this.
- Controls are `inline-flex items-center` with horizontal padding only. Icon-only buttons are square (`size-control`).
- Rows of controls use `flex items-center` and one `gap-*` from the spacing scale. Do not nudge alignment with margins, `top`, or `vertical-align`.
- Text and control on one line (label + select, name + button) must be vertically centered. A multi-line block beside a control aligns to the top.

**Spacing.** Use a 4px scale: 4, 8, 12, 16, 24, 32, 48, 64 (Tailwind `1, 2, 3, 4, 6, 8, 12, 16`). Use 8 inside controls and between related controls, 16 between groups, 24–32 between sections, and 48+ between page regions. Do not use odd values (7, 9, 11, 13) or asymmetric padding without a reason written in a comment.

**Type.** Libertinus Serif throughout. The size scale is `text-xs` 14 (captions, metadata), `text-sm` 16 (controls, secondary text), `text-base` 19 (body), `text-lg` 23 (subheadings), `text-xl` 26 (section and modal titles), and `text-display` for the page title only. Weights are 400 and 600. Body line height is 1.5; headings and controls 1.2. Muted text uses `text-muted`, never reduced opacity. Do not use uppercase labels, letter-spacing, or icon-plus-caption stacks as decoration.

**Shape and depth.** Controls, inputs, and panels use `rounded-md` (6px); cards and modals `rounded-lg` (8px); chips, pills, and progress tracks are fully round. Separate content with 1px `border-line` borders and whitespace. Shadows are reserved for floating layers (modals, toasts, popovers), and all use `shadow-float`.

**Color.** Keep color scarce: paper, ink, muted, line, surface, plus one accent. Accent marks the single primary action in a view, the current selection, and links. It is not decoration. There is at most one primary button per view or modal. Destructive actions use the danger token only on hover or in confirmation, since removal already has undo.

**Components.** Build from `app/ui.tsx` before writing new markup: `Button` (primary/secondary/ghost, md/sm), `IconButton` (square, `label` sets the accessible name and tooltip), `ToggleButton`, `Input`, `Select`, `Textarea`, `Badge`, `Card`, `List`/`ListItem` rows, `Modal` (Escape and backdrop close), `Tabs`, `Spinner`, `ErrorMessage`, and `Page`. Merge extra classes with `cn`. Pages add only layout utilities; a pattern used twice becomes a component or variant there. Generated Markdown uses the `.markdown` class in `globals.css`. Every interactive element needs hover, focus-visible (the shared outline), and disabled states, and a hit target of at least 32px.

**States and motion.** Loading uses `Spinner` next to text that says what is happening. A placeholder takes the size of what replaces it (a loading chat is a chat-sized card, a loading dialog keeps its subtitle line), and state kept in the browser that changes layout is applied before the first paint (the layout's script sets the theme and the subject chat's width), so nothing jumps as data arrives. MathJax loads when the app starts and typesets before paint once ready. Empty states are one plain sentence with at most one action. Errors appear next to the thing that failed, in `ErrorMessage`. Transitions are 150ms ease on color and background only. The exceptions are the topic tree: folders collapse with a 200ms ease-out grid-row transition and chevron rotation, and moved or new rows fade from `accent-soft` with `animate-flash`; both are disabled under reduced motion. Nothing bounces, slides in, or delays interaction.

**Layout and responsiveness.** Keep a single reading column with a comfortable measure (roughly 60–80 characters for prose). Check every change at 375px wide and in dark mode: rows wrap cleanly, nothing overflows horizontally, and control heights stay equal after wrapping.

**Restraint.** Before adding a heading, border, label, icon, or banner, remove one that is redundant. Prefer fewer, larger, well-spaced elements over many small ones. If two things look almost the same, make them identical.
